## 1. The split

BLUEPRINT §2 assumes the portal ID is unique across both Houses. For 136 IDs it is not: each is used by an LS recommended work and by a different RS sanctioned work. Phase 1/2 had stored each pair as one work, with the LS MP, district and description but the RS sanction, completion and payments. Each pair is now two works under the compound identity (portal_id, House). The LS half keeps work_key = portal ID; the RS half is keyed `<portal_id>-RS`. Nothing was re-ingested and no other Phase 1/2 logic changed (`app/ingest/p6_identity_split.py`, run by `scripts/run_identity_split.py` after `run_normalize.py`).

- Records now carrying a shared portal ID: **272** (136 LS + 136 RS) from 136 IDs.

Those are the populations the peer groups, portfolio shares, authority shares, cadences and near-duplicate blocks are computed over. "Only in before/after" are the 136 LS halves, which left the scored population as recommended-only works, and the 136 RS halves, which entered it.

- **near_duplicate is national by design.** Its TF-IDF vocabulary and phrase-frequency weights are fitted over every description (BLUEPRINT §6 "national phrase-frequency discount"). Removing 136 descriptions from scope and adding 136 others therefore nudges every vector.
