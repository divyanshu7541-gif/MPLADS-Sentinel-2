# Deploy notes: Vercel backend service

> [!WARNING]
> **The backend container refuses to start without `JWT_SECRET` and `DATABASE_URL`.**
> Set both in the Vercel project for **both Production and Preview** *before* this branch deploys.
> If either is missing, the whole API is down (5xx), not just login.

Environment variable **names** for the `backend` service in the root `vercel.json` (built from
`backend_v2/Dockerfile.vercel`). Values are never written here. Secrets go in Vercel → Project →
Settings → Environment Variables, for **both Production and Preview**.

## Required (set in the Vercel project)

The container refuses to start without these, because `APP_ENV` is pinned to production.

- `JWT_SECRET` — the token signing key, at least 32 characters. Checked at startup (`app/auth/tokens.py`).
- `DATABASE_URL` — the production Postgres. Checked at startup (`app/core/config.py`); the code default is for local development only.
- `CORS_ORIGINS` — the exact frontend origin(s), comma-separated, never `*`.

## Pinned in `backend_v2/Dockerfile.vercel` (do not set in the dashboard)

- `APP_ENV` — production mode, so the startup checks above apply.
- `TRUST_PROXY_HEADERS` — the rate limiter keys on the client IP that Vercel's proxy forwards, not on the proxy itself (`app/auth/ratelimit.py`).

## Never set on Vercel

- `WARM_CACHE` — the startup warm-up thread would hold one of the instance's two pooled connections for the whole warm-up, leaving one for requests on every cold start. It is off by default and only the compose files turn it on.

## Optional

- `GEMINI_API_KEY` — the copilot's free-form answers (`app/core/chat_config.py`); without it the copilot falls back to its local rule-based guide (`app/api/chat.py`). Set it in the Vercel project, never in the repo, and rotate the key before deploying.
- `ANONYMOUS_READ` — read-only `public` role for callers with no token (`app/core/config.py`, code default `true`). The frontend sends no token, so `false` takes the public site down.
- `DB_POOL_SIZE` — connections per instance (code default 2).
- `DB_MAX_OVERFLOW` — extra connections per instance above the pool (code default 0).
- `DB_POOL_RECYCLE` — seconds before a pooled connection is replaced (code default 300).
- `GATE_SLIM` — post-deploy gate only, not the service. Set it when running `backend_v2/scripts/postdeploy_gate.py` against the production database; it skips row counts for the 15 tables that are empty there, and still enforces the `risk_result` checksum and the flagged counts.

## Rate limits are per instance

The limiter keeps its counters in each instance's memory. On Vercel every warm instance counts on its own: the effective limit is the configured per-minute limit times the number of instances, and a cold start begins at zero. That's acceptable for slowing abuse, but it's not a hard global cap. A hard cap would need a shared store, and none is used. See `docs/security.md`, "Limitations".

## Personal-data masking (best effort)

Public (anonymous) API answers mask beneficiary and contact names, relatives' names, addresses and person-linked disability percentages in work descriptions (`backend_v2/app/serving/public_mask.py`). Phone and Aadhaar-shaped numbers are masked for everyone, as before. The masking is pattern-based and best effort, not a guarantee: unusual spellings, Hindi script, names with no title or keyword, and addresses with no keyword get through, and a rare ordinary word next to a name may be masked. Stored source text is never changed, so scoring and the risk_result checksum are unaffected. Logged-in accounts see the served text. Public search does not match description words in records that carry personal details; those records are still found by work key, MP, place, work type or authority. Graph Work labels get the same masking when the API answers; new graph builds also mask numbers before the 120-character cut. No serving table was rebuilt for this.

Known limits:
- Some names without clear markers (no title, and no "beneficiary", "s/o", "putra", "contact" or "resident of" next to them) can remain visible, for example a first name before "d/o" with no title in a long sentence, or a second person named later in the same description.
- One raw record was seen with a phone number that the phone masking (`redact.py`) does not catch. This is an older `redact.py` gap; it was not changed here.
- On the raw descriptions the scan changed about 1.7%; about 3.0% of works lose anonymous description-word search (they are still found by work key, MP, place, work type or authority).
