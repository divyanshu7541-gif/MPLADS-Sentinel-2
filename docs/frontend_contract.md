# Frontend API Contract (frozen at Phase 0)

This document is the frontend's contract with the backend. It was generated by
reading `frontend/src/services/api.js` line by line — every `fetch()` call in
that file is listed below, in file order. Response shapes were then verified
against the current implementation (`backend/app/api/routes.py`,
`backend/app/api/chat.py`, and the return statements of the `SentinelEngine`
methods they call in `backend/app/core/engine.py`), so the "Response shape"
column reflects what the *old* backend actually returns today, not a guess.

`backend_v2` (the new backend being scaffolded starting this phase) MUST
reproduce this contract exactly for every endpoint below before the frontend
is ever pointed at it (Phase 12 cutover). Phase 0 stubbed each route; since
the Phase 12 cutover every route is DB-backed and the frontend talks to
`backend_v2` (see "Phase 12 cutover" at the end). The old backend is archived
at `archive/backend_v1/`.

**Endpoint count: 32**, matching the 32 exported functions in `api.js`.
(`backend/app/api/routes.py` additionally defines `/api/health`, `/api/load`,
`/api/categories`, `/api/analytics/overview`, `/api/analytics/trends`, and
`/api/investigations/{investigation_id}` — none of these are called from
`api.js`, so they are not part of the frontend contract and are not listed
here. `/api/health` is still stood up in `backend_v2` as infra plumbing for
container healthchecks, not because the frontend needs it.)

## House column

MPLADS covers both Lok Sabha and Rajya Sabha MPs; Rajya Sabha MPs represent a
*state*, not a constituency. A per-MP "House" filter/field is planned for a
later phase (referenced in the working plan as §5/§6, which this pass did not
have direct access to — treat these marks as an inference to confirm at
Phase 1 kickoff, not a settled spec).

The column below marks `planned` for dataset-wide listing/aggregate endpoints
and the MP↔constituency graph (where House changes the relationship model),
and `—` for single-entity-detail lookups, write actions, and structural/
dataset-level endpoints where a House *filter* wouldn't apply. Nothing is
implemented for House in Phase 0 — this is a forward-looking marker only.

**Phase 3 update.** Seven endpoints now accept an optional query parameter
`house=LS|RS` and are marked `optional house=LS\|RS` below: #1 summary,
#2 queue, #4 analytics, #9 map-data, #10 map-works, #11 map-filters and
#12 graph-data. `LS` means the 18th Lok Sabha and `RS` the sitting Rajya
Sabha; those are the only two houses in scope.

- **Backward compatible.** Omitting `house` behaves exactly as before
  (both houses). Any other value returns 422. It is purely additive: no
  response shape changes.
- **A display filter only.** It selects which works are reported. Peer
  groups and baselines are built over both houses together
  (BLUEPRINT.md §6), so a work's baseline is identical whether or not a
  house filter is applied.
- **Live since the Phase 12 cutover.** (Until then the handlers were stubs
  and the frontend still talked to the old backend, which ignored the
  parameter.) All seven endpoints now really filter; LS + RS totals add up
  to the unfiltered total.
- **Constituency-scoped features** (#17, #19, #24 and the map drill-down)
  do not take `house`. The frontend shows an explicit "not applicable for
  Rajya Sabha" state for them when RS is selected, because Rajya Sabha MPs
  represent a state, not a constituency.
- **Still `planned`:** #7, #15, #26, #27 and #31.

## Notes for `backend_v2` stub implementers

- Endpoints #25, #28, #29, #30, #32 use the path parameter name `project_id`
  in both `api.js` and the old router, but the underlying engine methods take
  a `record_id` — there is no separate "project" concept in the current data
  model. Preserve the `project_id` path parameter name in `backend_v2` since
  that's the literal contract the frontend calls (`/api/risk/{project_id}`,
  etc.) — it happens to be a record id.
- Endpoints #9, #10, #14, #26, #31 return a bare JSON **array**, not an
  object — this matters for stub/contract tests, which must not assume every
  response is a dict.
- `/api/queue`'s `risk_level` query param is a legacy alias for `priority`
  (old router does `priority or risk_level` server-side); same for
  `/api/map-data` and `/api/map-works`. Phase 0 stubs should accept both
  params without erroring, even though they're not applied to anything yet.

## Phase 9 additions (map endpoints, all additive)

Endpoints #9, #10, #11, #22, #23 and #24 are DB-backed from Phase 9 (see
`docs/phase9_report.md`). Every documented key is kept, and new keys are only
added. No endpoint gained a `house` parameter.

- **Response headers (all six):** `X-Map-Run-Id`, `X-Map-Data-As-Of` and
  `X-Map-Is-Latest` name the analysis run being served. When the published run
  has no complete map build, the last complete build is served with
  `X-Map-Is-Latest: false`. #9 and #10 are bare arrays, so these labels
  travel in headers.
- **#10 map-works headers:**
  - `X-Location-Precision: approximate_constituency_level`, plus
    `X-Location-Precision-Note`.
  - `X-Total-Count` (matching works), `X-Returned-Count`, `X-Map-Works-Cap`
    (3000) and `X-Sampled`.
  - `limit` defaults to, and is capped at, 3000.
- **#10 new row keys:** `location_precision`, `house`, `district` and
  `work_location_state`.
- **#10 optional `redelimited` (additive, 2026-10-03):** `redelimited=true`
  (needs `state`, else 422) returns that state's Lok Sabha works in the seats
  the coverage data marks re-delimited (`geo_name_crosswalk` method
  `redelimited_boundary_not_available`). They have no stored point, so
  `latitude` and `longitude` are `null`, as stored; the response adds
  `X-Placement: state_level_redelimited`. Same row keys, filters and cap.
  Omitted or false, the response is unchanged (these works stay out). Reads
  `map_work` and `geo_name_crosswalk` only.
- **#9 map-data new row keys:**
  - `area_key` and `location_precision`.
  - `insufficient_data`: true when an area has fewer than 10 works. Rates and
    averages are then `null` while counts stay visible.
  - `not_evaluated`.
  - `X-Min-Works-For-Rate` header.
- **#9 map-data optional `level` (additive, 2026-10-02):** `level=state` returns
  one row per state, for the Rajya Sabha map (members represent a state). The
  state is where the works are located, not the member's own state. Rows carry
  the same metric keys, with `Constituency: null`, `level: "state"` and
  `state_basis: "work_location"`, and the same small-number rule. Works with
  no located state are left out. Omitted, or `level=constituency`, returns the
  constituency rows unchanged (so `house=RS` alone is still `[]`). Any other
  value is a 422. Reads `geo_metric` (or `map_work` when searching or scoped)
  only. No schema or scoring change.
- **#22 geojson:**
  - Versioned (`ETag`, `X-Geo-Version`, `If-None-Match` → 304) and gzip-able.
  - Feature properties: `dataset_state`, `dataset_constituency`, `area_key`,
    `pc_no`, `source_pc_name` and `match_method`.
  - Top-level `metadata` gives source, licence and boundary vintage.
  - Additive (2026-10-03): the Ladakh seat is served as the Admin2 Ladakh
    state shape (built with Admin2's Jammu and Kashmir so the two meet with
    no gap), and that feature alone carries `clipped_to_state: "Ladakh"`
    (display only; the stored geometry is unchanged).
- **New endpoint (additive, 2026-10-03): `GET /api/boundary-outlines`.**
  Display-only shapes, built from `geo_area` rows already loaded; no table is
  written. GeoJSON `FeatureCollection`, versioned like #22 (`ETag`,
  `X-Outlines-Version`, `If-None-Match` → 304), with `metadata.outlines_version`.
  - `kind: "national_outline"`: the Survey of India-derived national outline
    (`geo_area` national `IN`), simplified to about 1 km (about 130 KB of the
    response). Properties: `name`, `source`, `licence` and `version`. The Map
    has no tile layer: it draws this shape as an opaque land fill and as a
    thin line above the seat fills.
  - `kind: "state_border"`: every Admin2 state shape (`geo_area` level
    `state`), simplified to about 1 km. Properties: `key`, `name`, `source`,
    `licence` and `version`. Drawn as thin border lines under the seats.
  - `kind: "redelimited_state"`: one state-level shape per state whose seats
    the coverage data marks re-delimited (today Assam and Jammu and Kashmir),
    simplified to about 500 m. Properties: `state`, `match_method`
    (`redelimited_boundary_not_available`), `reason`, `source`, `licence`,
    `version`, and `marker_lat` / `marker_lon`: a point computed inside the
    served shape (shapely `representative_point`), where the Map places the
    state's works. It never carries a metric or risk field; the Map colours
    it from #9 `level=state`.
  - A failed build is a 503. The Map loads without the outlines (it gives up
    after 20 s) and shows a one-line note.
- **#23 geographic-coverage new keys:** `match_methods`, `redelimited_count`,
  `no_boundary`, `sources`, `works_total`, `works_with_marker`,
  `works_district_unlocated`, `location_precision`, `note` and `served`.
  `centroid_fallback_*` is always 0, because v2 never falls back to a centroid.
- **#24 constituency-intelligence new keys:**
  - Always: `found` and `served`. An unknown name still returns 200 with
    zeros and `found: false`.
  - When the constituency is `Sitting Rajya Sabha`: `applicable: false`,
    `house: "RS"` and `not_applicable_reason`.
  - For a Lok Sabha constituency: `applicable: true`, `house: "LS"`,
    `area_key`, `boundary_status`, `min_works_for_rate`,
    `location_precision`, `insufficient_data`, `not_evaluated`,
    `signal_high_threshold` and `confidence_distribution_note`.
    `confidence_distribution` was `{}` in Phase 9 (no confidence bands);
    since Phase 12 it counts the old engine's bands, like every other
    endpoint (see "Phase 12 cutover").
- **Errors:** invalid `priority`/`risk_level`, `limit < 1`, a search over 100
  characters or containing NUL, and an invalid `house` all return 422. A
  database failure returns 503.
- **New endpoint (not called by the frontend):**
  `GET /api/geo/areas/{area_key}/works?page&page_size&priority&stage&search`
  returns a paginated list of every work in one constituency (`pc:..`) or
  district (`dist:..`), including works without a marker.

## Phase 10/11 additions (all additive)

- **#12 graph-data** is DB-backed from Phase 10 (`docs/phase10_11_report.md`):
  nodes/edges are read from a per-run graph built offline by
  `scripts/run_entities.py`, never from a live join. `house` now really
  filters: only edges whose backing work is that House are returned; nodes
  are unfiltered (a node can appear with no edges under a House filter).
  `weight` is an additive edge field. Bounded: at most 25 of each entity type
  plus their bridging works, documented in the report.
- **New endpoint (not called by the frontend):**
  `GET /api/entities/{entity_type}/{entity_id}` (`entity_type` one of
  `payee`, `implementing_agency`, `district_authority`, `mp_tenure`) returns
  that entity's profile and every `entity_metric` row computed for it in the
  published run (BLUEPRINT.md §8). Every row's `denominator`, `interval` and
  `peer_definition` are present whether or not the metric was evaluable.
  Unknown `entity_type` is 422; an entity that doesn't exist is 404.
- **#20/#21 chat/status and chat:** shapes unchanged. The chatbot's
  methodology text is now generated from the live fusion/confidence
  configuration (`app/analytics/methodology.py`) instead of hand-written,
  and a message naming a specific work (e.g. "why is work 133166 flagged")
  is answered from that work's actual stored `risk_result` row, never a
  guess -- if no such row exists, the reply says so explicitly.

## Phase 12 cutover (all additive)

Every endpoint in the table is now DB-backed and reads the published run.
Most read `served_work`, a per-run read model built offline by
`scripts/run_serving.py`, and `case_event` (`docs/phase12_report.md`).
Every documented key is kept, and new keys are only added. The frontend dev
proxy (`localhost:8000`) now reaches backend_v2 (`docker-compose.yml`).

- **Population.** Risk figures (#1, #2, #4, #25–#31) cover **scored** works
  only. Those are the sanctioned and completed works that have a stored
  `risk_result`. Recommended-only works have no risk, tier or confidence:
  they are `null`, never 0.
  - #3 answers them with `risk_level: "NOT_EVALUATED"`.
  - The Queue's `stage=RECOMMENDED` filter is therefore always empty.
  - MP and constituency profiles (#16–#19) count all works for stage and
    amount figures, and scored works for risk figures (`scored_works`,
    `risk_rate_basis`).
- **Vocabulary.** The frontend translates a fixed vocabulary, so values are
  mapped onto it (`app/serving/labels.py`):
  - Stages are upper case. This includes the map endpoints #9–#11, which
    served `Completed`/`Sanctioned` in Phase 9.
  - Signals use the old names, with the v2 definition in the additive
    `signal_description`.
  - Confidence bands are the old engine's: HIGH ≥ 0.7, MEDIUM ≥ 0.5.
  - Signal strengths are the old engine's: HIGH > 0.7, MEDIUM > 0.3.
  - Recommendations reuse the old engine's exact sentences.
- **#2 queue:**
  - Accepts `mp` as an alias of `mp_name`, and applies `risk_level` as well
    as `priority`. The Queue page sends `mp` and `risk_level`; the old
    router ignored both.
  - `page ≥ 1`. `page_size` is between 1 and 200 (default 50); anything
    else is 422.
  - Text filters are literal substring matches, never regex.
  - Additive row key: `house`.
- **#3 record, #25 risk, #28–#30, #32.** Unknown ids return 404, as before.
  - Additive keys: `house`, `not_evaluated_signals`, `evidence_facts`,
    `compliance_flags`, `served`.
  - `risk_assessment` also gains `n_eligible`, `pre_multiplier`,
    `confidence_components`, `config_name`, `scored` and
    `not_scored_reason`.
  - Evidence items also gain `signal`, `signal_description`, `direction` and
    `tail_percentile`.
- **#13 investigate.**
  - The actor is **never** taken from the body. `reviewer` is accepted and
    ignored.
  - Phase 12 had no auth, so its entries recorded a labelled placeholder
    actor (`actor_is_placeholder: true`). Superseded in Phase 13: the actor
    is the token's account (see "Phase 13 security" below).
  - Entries are persisted append-only in `case_event`. `previous_status` is
    the work's last decision.
  - Unknown record returns 404. Additive keys: `event_id`,
    `actor_is_placeholder`.
- **#32 recalculate** means "flag for next run" (plan §5). It records a
  `recalculate_requested` event and returns the stored result with
  `status: "flagged_for_next_run"` and `recomputed: false`. It never writes
  `risk_result`.
- **#26 risk/top** is no longer shadowed by `/api/risk/{project_id}`. The old
  router registered them in the wrong order.
- **Errors.** A database failure returns 503 on that endpoint only.
- **`POST /api/load` is removed.** It had zero frontend callers.

## Phase 13 security (additive; docs/security.md)

Every documented key and shape is unchanged. What changed is who may call
what, plus a few new error codes.

**Read endpoints.** These are all table rows except #13, #14 and #32.
- They work without a token as the built-in public role (national,
  read-only) while `ANONYMOUS_READ=true`, the default. The unchanged
  frontend sends no token.
- With `Authorization: Bearer <token>`, every figure is restricted in SQL to
  the account's scope (House, state, district authority or MP).
- An out-of-scope record reads as 404.
- #12 graph-data is refused (403) to a state-, district- or MP-scoped account,
  because it is a national aggregate.
- An invalid or expired token is always 401. It never falls back to public.

**Case endpoints.** #13 investigate and #32 recalculate require an
investigator, supervisor or admin token, and #14 audit-trail requires the
same roles. Without a token they return 401; with another role, 403.
- The `reviewer` recorded on #13 is the token's account. The body's
  `reviewer` is ignored.
- Entries gain `event_type`, `prev_hash` and `event_hash` (the hash chain).
  `actor_is_placeholder` is now false.

**#12 graph-data, public view.** Payee nodes typed individual or unclassified
are labelled `Payee (name withheld in public view)`. Authenticated accounts
see names.

**#21 chat.**
- Rate-limited: 429 with `Retry-After`.
- Bounded input: `message` ≤ 2,000 characters, `history` ≤ 20 items. Over
  that returns 422.
- Scope-aware: a work outside the caller's scope is answered as having no
  stored result.
- Additive (2026-10-02): constituency and MP questions are answered from the
  served data with `source: "lookup"`; those replies also carry `links`
  (`[{label, href}]`, existing routes only), `suggestions`
  (`[{label, message}]`) and, after "compare with another ...", `context`.
  The request may echo that back as optional `context`
  (`{compare_with: {kind: "mp"|"constituency", name}}`, name ≤ 200
  characters, unknown keys ignored, the name re-checked server-side).
  `reply` and `source` are unchanged for every other answer.

**Search.** `search` on #2, #9 and #10 is rate-limited (429). On #2 it is
bounded to 200 characters (422 over that).

**New endpoints.** None of these is called by the frontend.

| Endpoint | Purpose |
| --- | --- |
| `POST /api/auth/login` | Exchange a username and password for a token |
| `GET /api/auth/me` | Who the token belongs to, and its scope |
| `GET /api/cases/{record_id}/events` | Export one case's events, with hashes |
| `GET /api/audit-trail/verify` | Recompute the case-event hash chain |
| `/api/audit/samples…` | The randomised audit sample (see docs/security.md) |

**CORS.** An explicit allowlist (`CORS_ORIGINS`), without credentials.

**Deployed site (2026-10-02).** The contract suite (`backend_v2/tests/test_contract.py`) has not been
run against the deployed Vercel site; it has run only against local stacks.
